# FlowFreeze model card

## Models
1. **Fraud model**: `HistGradientBoostingClassifier` + isotonic calibration (scikit-learn). Output = calibrated P(fraud). Alert rule (business policy, separate from the model): `P(fraud) × amount ≥ τ`, τ tuned on a validation window for ≤2% false-alert rate.
2. **Next-move model**: calibrated multiclass gradient boosting: P(forward / cashout / other) in the next 30 min for money that just landed. Trained on transfers only.
3. **Anomaly layer**: Isolation Forest on mostly-legitimate traffic, reported as a percentile (unsupervised sanity check).
4. **Explanations**: exact Shapley values against a typical legitimate transaction (additive: Σφ = P(tx) − P(baseline)).

## Evaluation protocol
Time-based split (train first 60% / validation 20% / test last 20%). Metrics in `data/processed/evaluation.json` are regenerated by `python -m ml.train_fraud_model`: ROC-AUC, PR-AUC, recall at fixed FPR, Brier, ECE, comparison with a **fixed-rule baseline** and **logistic regression**, fairness slices (false-alert rate by account age, channel, merchant, legitimate look-alikes).

## Honest limitations
- Synthetic data: performance numbers show the pipeline works, not production accuracy.
- The next-move model is only modestly better than the majority-class baseline in accuracy; its value is as a calibrated cash-out likelihood (see `cashout_pr_auc` vs base rate and the threshold table).
- Fairness slices show a higher false-alert rate for new accounts and the agent channel (the simulator makes fraud more common there). Mitigation: those alerts go to analyst review, never to automatic action; re-check on real data; consider group-aware thresholds only with compliance sign-off.
- Alert threshold is a pilot starting point, not an operations-approved value.
